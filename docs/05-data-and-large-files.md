# Data & Large Files — Why They're Not in Git

> **TL;DR:** This repository tracks **source code, configuration, and docs only.**
> The large datasets, trained models, downloaded weather files, databases, and
> virtual environments are **kept local** and are intentionally excluded via
> [`.gitignore`](../.gitignore). This page explains what's excluded, *why*, and
> how to get the data back on a fresh checkout.

---

## Why we don't commit data to Git

Git stores the full history of every file forever. Committing large, frequently
changing binary data (CSV datasets, `.grib2`/`.tar` weather files, `.keras`
models, SQLite DBs) causes problems that don't go away even if you later delete
the files:

- **GitHub hard-rejects any file over 100 MB** and warns above 50 MB. Several of
  our weather archives are **1–1.6 GB each** — they simply cannot be pushed.
- **The repo balloons permanently.** Before this cleanup the three sub-projects
  carried ~4.2 GB, ~3.3 GB, and ~903 MB of git history — mostly data. Clones and
  fetches become painfully slow for everyone.
- **Data is reproducible / re-fetchable**, so versioning it in git adds cost with
  little benefit. Code is the thing we actually need to version.

This follows standard practice: **code in Git; data in object storage, a data
archive, or regenerated by the pipeline.** (For ML reproducibility specifically,
tools like DVC or Git LFS exist, but for a dataset this large and re-fetchable,
keeping it local + documented is the simplest correct choice.)

## What is excluded (kept local only)

| Path / pattern | What it is | How to get it back |
|----------------|-----------|--------------------|
| `**/data/`, `**/data_old (v2.1)/`, `**/data_old(v3.1)/` | Historical grid + carbon-intensity CSV datasets (v2.1 / v3.1). | Reference/fallback data; regenerated by the API ingestion pipeline, or copy from a teammate / backup. |
| `**/CI_forecast_data/` | Carbon-intensity forecast outputs per region. | Produced by running the forecasting pipeline. |
| `**/real_time/` | Real-time per-region working data. | Produced by the daily ingestion pipeline. |
| `**/saved_first_tier_models/`, `**/saved_second_tier_models/` | Trained Keras/TensorFlow ML models (two-tier forecaster). | Produced by model training/retraining; or copy from backup. |
| `**/downloaded_files/`, `*.grib2`, `*.tar`, `*.nc` | NCEP GFS weather files from NCAR RDA. | Re-downloaded by the **automation tool** (`UCSC_OSRE_CC_automation_tool`). |
| `*.sqlite3`, `*.db`, `db.sqlite3` | Local databases (e.g. Django dev DB). | Recreated with `python manage.py migrate` (+ ingestion). |
| `**/.venv/`, `venv/`, `env/` | Python virtual environments. | `pip install -r requirements.txt`. |
| `node_modules/`, `dist/` | Frontend dependencies & build output. | `npm install` / `npm run build`. |
| `.env`, `.env.*`, `rdams_token.txt`, `*.key`, `*.pem` | **Secrets & credentials.** | Never commit. Copy from your own secure source; see `.env.example` files for the expected variables. |

> `.env.example` files **are** committed on purpose — they document which
> environment variables each project needs, without exposing real values.

## Getting a fresh checkout running

A clean `git clone` will **not** include the data above. To get each project
working:

1. **Frontend** (`CarbonCastUI/web`): `npm install`, then create `web/.env` from
   `web/.env.example`.
2. **API** (`UCSC_CarbonCast_API/CarbonCast`): `pip install -r requirements.txt`,
   create `src/CarbonCastAPI/.env` from `.env.example`, then
   `python manage.py migrate`. The API falls back to CSV files when the DB is
   empty, so you may also need to copy the `data/` folder from a backup.
3. **Automation tool** (`UCSC_OSRE_CC_automation_tool/CarbonCast`):
   `pip install -r requirements.txt`, add your NCAR RDA token to
   `rdams_token.txt`, and run it to repopulate `downloaded_files/`.

See [`../HANDOFF.md`](../HANDOFF.md) and the per-project guides in this folder for
the full instructions.

## If you ever DO need to share the data

Don't force it into git. Prefer:

- **Object storage** (S3 / GCS / a university file server) for the rotating
  weather + dataset files — share a path or signed URL.
- **A data archive** (Zenodo / Figshare) if it's a fixed, citable dataset.
- **Git LFS or DVC** only for a small, curated set of files you genuinely need
  versioned alongside the code (mind the storage quotas/cost).
